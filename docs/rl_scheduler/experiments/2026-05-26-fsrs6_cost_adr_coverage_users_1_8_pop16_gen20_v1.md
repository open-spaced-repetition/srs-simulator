## Question

Rerun Cost-ADR on users 1-8 with the coverage-aware objective enabled, keep the
matched pop16/gen20 budget, use the multi-user in-process training batch path,
and compare against ADR plus the adaptive-parameter and other already evaluated
portfolio strategies.

There is no scheduler or artifact named `ADP` in the repo. I treated that request
as the existing adaptive-parameter line, reported as FSRS6 AP and Anki SM2 AP in
the published comparison context.

## Run

```bash
uv run python experiments/rl_scheduler/run_experiment.py \
  --config experiments/rl_scheduler/configs/fsrs6_cost_adr_coverage_users_1_8_pop16_gen20_v1.toml \
  --stage all \
  --run-id fsrs6_cost_adr_coverage_users_1_8_pop16_gen20_v1_markov_off
```

All formal stages passed: `dry-run`, `preflight`, `stage-baseline`,
`train-overfit`, `sweep`, `build-pareto`, and `analyze-pareto`.

The configuration keeps the formal Cost-ADR budget: one 24-parameter policy per
user, CMA-ES `population_size=16`, `generations=20`, `sigma0=1.0`, zero initial
mean, coefficient bounds `[-12, 12]`, and the 16 goal cost weights
`0,1,2,4,8,16,32,48,64,96,128,192,256,384,512,1024`.

Coverage-aware training objective:

- `coverage_objective_enabled = true`
- `coverage_min_budget_span = 0.90`
- `coverage_min_target_span = 0.90`
- `coverage_penalty_weight = 0.05`

## Interpretation

Coverage-aware Cost-ADR fixed the coverage collapse that showed up in the pure-HV
Cost-ADR training diagnostics, but it did not produce a better scheduler. The
external FSRS6 HV is about half of ADR's, and the LSTM HV is negative relative
to the FSRS6 baseline. The coverage-aware run also gives up the positive
same-budget memory lift AUC that ADR and oracle distill keep.

The run is still useful diagnostically: multi-user batch parallelism worked,
coverage constraints were met for all eight users during training, and external
coverage became very high on both FSRS6 and LSTM. The tradeoff is too expensive:
the additional coverage mostly buys interpolation span, not better Pareto
quality.

Promotion decision: do not promote `fsrs6_cost_adr` coverage-aware pop16/gen20
over ADR. Keep ADR pop16 or oracle stationary finite distill w11 as stronger
formal baselines, depending on whether the priority is LSTM generalization or
FSRS6 HV.
